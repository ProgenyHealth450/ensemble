# Inputs

- `Dimension`: one of `commit-messages`, `code-quality`, `test-coverage`, `ai-adoption`, `documentation`, `code-review`. If missing or unknown, stop and say so.
- Optional output path or `REPORT_PREFIX` (means `docs/assessment/team-<REPORT_PREFIX>-<dimension>.md`). With one, save the full report there and return a summary only (max 5 lines); without, report in your response and save to `docs/assessment/team-<dimension>.md` only if asked.

Follow only the matching `## Dimension:` section below, plus the shared rules.

# Privacy and use guard

Report team-level aggregates by default. Per-author tables and scores only when the caller explicitly asks for individual results, and only for authors with at least 10 commits in scope (group the rest as "others"). Git signals are partial proxies: never present them as a performance rating or use them for HR decisions.

# Shared rules

- Data: local git only unless the section says otherwise. Use simple `git` commands; avoid `find -exec`, `xargs` and complex pipelines, prefer your runtime's file-discovery, read and search tools.
- Cite `file:line` and specific numbers ("127 commits without body"); cite 3 examples then "47 more similar". Tables over paragraphs, no filler.
- Missing data: write "No evidence found in local git" (never "N/A"), add `[confidence: MEDIUM - requires API to verify]`, adjust the score.
- Score every dimension `<1.0-5.0> / <Letter>` with a one-line rationale: number first, then derive the letter per the Scoring Scale in `skill://assessment-report-suite`. Never assign a bare letter.

Return summary (max 5 lines): headline metric, top issue or contributor pattern, `Score: <1.0-5.0>/<Letter>` with one-word rationale.

# Dimension: commit-messages

1. Sample 50-100 commits across authors: conventional format (feat:, fix:, docs:), subject length (50-72 chars), body for complex changes, issue references, breaking-change markers.
2. Classify each: Excellent (conventional + body + context), Good (conventional or clear subject), Acceptable (brief but descriptive), Poor ("fix", "update", "WIP", single char, empty).
3. Report % following conventions, quality distribution, improvement trend over time, common issues with 3 examples each.

# Dimension: code-quality

1. Indicators in history: refactoring/cleanup commits, bug-fix patterns (quick fix vs proper solution), PR/merge size (small focused vs large batch), TODO/FIXME density and who adds vs removes it, large-file introductions, technical-debt introduction vs removal.
2. Attribute patterns where possible: who creates debt, who cleans up, who struggles with test coverage.
3. Assess consistency across authors, improving vs degrading trends, ownership of critical components.

# Dimension: test-coverage

1. Find test files (unit, integration, E2E, coverage reports) and test-to-source file ratios; attribute authorship via `git blame`.
2. Who writes the most tests, who rarely does, who writes quality tests (not just coverage), who introduced untested critical paths.
3. Coverage by component/module, gaps in critical paths, test-avoidance patterns. Data: local git plus file discovery.

# Dimension: ai-adoption

Data: local git plus code-pattern analysis; AI tool usage statistics (e.g. Copilot) are not available from local git.
1. Code signals: `// Generated by`, `// AI-Generated`, structured TODO comments, boilerplate density, uniform formatting/indentation across unrelated files. Search with your text-search tool for `// TODO:`, `# TODO:`, `// Generated`, `// AI`.
2. Commit signals (simple patterns only): `git log --format="%ae|%s" -n 200` filtered for `ai|pi|generated|auto` markers; very short intervals between commits on different files; large PRs with uniform style; "generated"/"created"/"added tests" messages.
3. Effectiveness: quality consistency, boilerplate vs organic ratio, test coverage in AI-assisted files. Report tool integration: CI/CD AI checks, code-review AI tools, AI attribution policy (Yes/No).

# Dimension: documentation

1. Find docs: `.md` in root and `docs/`, READMEs, API docs, ADRs, runbooks, guides, wiki contributions.
2. Attribute via `git blame` on doc files and commits touching `docs/`.
3. Assess completeness (does it explain things), currency (last updated), clarity (structure, examples), and coverage (what is documented vs not, e.g. "6 of 9 services have no README"). Table: Area / Documented / Last Updated.

# Dimension: code-review

Local git CANNOT verify PR reviews: history shows who merged, not who reviewed. Review comments and approvals need `gh pr list --state merged --limit 100` or `az repos pr list`; shell `git`, `gh` and `az` only.
- If review data cannot be obtained (tools unavailable or unauthenticated), cap the numeric score at 2.0 (grade D) unless verifiable data is itself worse, and note "Cannot verify peer review from local git".
1. Gather what git shows: merged PR commits (`git log --merges --format="%ae|%ae" -n 100`, `git shortlog -sne HEAD`) and `Co-Authored-By` collaboration signals.
2. Include a Data Availability section: PR review and approval data **NOT available from local git** `[confidence: LOW - requires API]`, with the `gh`/`az` command to get it.
3. Merge ownership (who completes PRs) and participation rate; flag concentration ("9 of 12 merges by one author").
